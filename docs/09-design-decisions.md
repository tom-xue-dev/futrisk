## 2. 对模糊需求的理解与处理

### 2.1 "单日浮亏达到预设阈值（如初始资金的 3%）"
这句话有三处需要定义：什么是"单日浮亏"，"初始资金"指什么，"达到"是否包含等于。

**"单日浮亏"的三种可能口径**：

| 口径 | 计算方式 | 问题 | 本系统 |
|---|---|---|---|
| A. 按开仓价计算的持仓浮亏 | Σ(最新价 − 开仓价) × 乘数 × 手数 | 把前几天的盈亏混进"单日"；昨天赚了钱的持仓，今天亏损要先吃掉昨天的利润才会触发 | 不采用 |
| B. 按昨结算计算的持仓浮亏（纯浮亏） | Σ(最新价 − 昨结算或今日开仓价) × 乘数 × 手数 | 平掉亏损仓位之后浮亏"归零"，账户可以反复实现 −3% 的亏损而继续开仓，熔断被绕过；不含手续费 | 保留为可选口径 `floating_pnl_pct_init` |
| C. 昨结起算的当日盯市总盈亏 | 动态权益 − 静态权益 = 平仓盈亏 + 持仓盯市盈亏 − 手续费（静态权益已包含当日出入金） | 与期货公司结算单的逐日盯市口径一致（平仓盈亏 + 持仓盯市盈亏，再扣手续费）；平仓不能绕过；出入金不会被当成盈亏 | **默认口径** `daily_pnl_pct_init` |

决定：默认用口径 C（01 §8.14、ADR-008），把 `risk_rules.yaml` 中 `daily_loss` 规则的指标换成 `account.floating_pnl_pct_init` 即可切换到口径 B（没有单独的开关）。两种口径的指标都在 02 §7.6 中定义。

- **"初始资金"**：取 `accounts.yaml` 中每个账户的 `initial_capital`（演示账户为 500 万~2000 万），首日建账时写入日初快照，此后随快照逐日延续，不取当日的静态权益。这样阈值是一个固定金额（1000 万的账户为 30 万），不会因为账户前几天盈亏而漂移。按静态权益计算的同一指标（`daily_pnl_pct_sod`）也提供，供需要时配置。
- **"达到"**：规则的比较符是 `<=`，即当日盈亏 ≤ −3% 时越线，恰好等于也算达到。
- **验收用例对两种口径都成立**：内核级验收测试构造了"当日开仓、没有平仓"的账本，此时口径 B 与口径 C 只差当日手续费，两种口径各测一遍都触发熔断（`tests/unit/engine/test_engine_acceptance.py`）。

**"阻止该账户继续开仓"**：

| 需要确定的问题 | 本系统的处理 | 理由 |
|---|---|---|
| 已经挂在柜台上的开仓单算不算"继续开仓"？ | 算。熔断时立即撤销该账户所有挂着的开仓单，包括还在路由中和状态未知的 | 挂单成交同样增加风险敞口；不撤等于没有阻止 |
| 平仓是否也禁止？ | 不禁止。平仓单跳过账户状态与限制、资金和 what-if 三步检查，也不受行情质量和 kill switch 的限制（行情质量不是 OK 时连胖手指检查也跳过）；其余检查（合约与数量、交易时段、价格、报单速率、可平量、自成交）照常 | 禁止平仓会让风险无法降低，违背熔断的目的 |
| 由谁、在什么时候解除？ | 风控经理带理由重置（需要 RISK_MANAGER 或 ADMIN 角色，写审计），或者换日 | 熔断是"需要人看一眼"的事件，不能随行情反弹自动解除 |
| 熔断能否被系统故障绕过？ | 服务重启不能：锁存状态逐次落盘，重启后恢复（§6.5）。配置热加载删除或停用规则时锁存保持；锁存的规则和级别仍在、只是定义被修改时，状态机立即改用新定义但保留锁存标志：只改阈值或 `latch` 时仍然锁存，把动作改成熔断以外的动作（例如告警）时账户立即离开 HALTED、恢复开仓（§6.4） | 验收要求"自动触发并阻止"，必须在故障下也成立 |

### 2.2 "接入至少 2 个行情源"
题目没有说两个源是否必须是真实的、是否必须独立。本系统的理解是：**行情最终都来自交易所，生产环境的冗余体现在分发链路上**（不同的前置、厂商和协议，故障相互独立），所以"两个源"的价值在于两条互为备份、可以互相校验的链路。

| 源 | 形态 | 在系统中的作用 | 状态 |
|---|---|---|---|
| Feed A（模拟，仿 CTP） | WebSocket 推送，500ms，带全局序号和 epoch，可续传、可重放 | 延迟最低的实时源 | 已实现，默认启用 |
| Feed B（模拟，仿厂商接口） | HTTP 轮询，1s，字段格式不同，没有序号，不能重放 | 异构备份源，交叉校验 | 已实现，默认启用 |
| 新浪 hq.sinajs.cn | HTTP 轮询，默认 1.5s，GB18030 文本，时间戳只到秒 | 唯一真实的源：真实 tick 录制（真实行情样本），真实行情部署中的第三个源 | 适配器与录制工具已实现；运行时默认关闭 |

Feed A 和 Feed B 的传输方式（推送与轮询）、数据格式、有没有序号和重放、故障注入点都不同，任何一路断开、延迟、乱序或者发来坏数据，另一路都能接上，并参与同成交量价格一致性的交叉校验（01 §8.13）。两路都可信时，谁出示了更新的市场状态谁推进水位，不按优先级挑选；`feeds.yaml` 中的优先级只在日终合成规范 tick 文件、去掉重复状态时使用。两者共用上游 sim-exchange，sim-exchange 出问题相当于交易所本身出了问题，系统走"全部数据源中断"的路径：相关合约标为 STALE/UNKNOWN 并禁开。

演示时不启用新浪：模拟价格和真实价格不是同一个市场，两边的状态会被当成同一个合约的行情互相比较和排序，结果没有意义。设想中"由 sim-exchange 转发新浪真实价格、三路源描述同一个市场"的 live 档没有实现（TD-12）。

### 2.3 模拟数据的设计理由
题目允许使用模拟数据，但要求说明理由。选择自建虚拟交易所（sim-exchange），理由如下：

| 需要 | 真实行情做不到的地方 | 虚拟交易所的做法 |
|---|---|---|
| 随时可演示 | 真实行情只在交易时段有数据；开发与交付期间的交易日很少（2026-09-25 中秋休市，10-01~10-07 国庆休市） | 7×24 运行；演示模式下市场时钟由 supervisor 维护，可以向前跳到下一个开盘、收盘前或任意更晚的时刻（01 §8.2） |
| 结果可复现 | 真实行情每次都不同 | 价格引擎每个交易日第 k 步的随机数只由（种子、交易日、k）决定 |
| 能验证容错 | 无法让真实行情源按需断线、跳号、乱序、发坏点 | 故障注入接口：断线（关闭或静默）、跳号、重复、乱序、延迟、停止更新、坏点、畸形数据、交易所重启、柜台断线、柜台强平（02 §9.5） |
| 能验证验收场景 | 无法让真实市场按需下跌 3% | 场景剧本：`breaker` 让黑色板块分三段下跌，使 ACC3 依次越过 −2%、−2.5%、−3%（`config/scenarios/breaker.yaml`） |
| 需要一个柜台 | 没有期货公司的交易通道 | 仿 CTP 语义的模拟柜台：报单、撤单、回报、查询、补回报，委托和成交落 `sim.db`，重启后序号不重复（02 §9.4） |

模拟数据尽量贴近真实：

- 以 `sim.yaml` 中配置的昨结算价为初值，按合约配置年化波动率、成交速率和持仓量；品种之间用 Cholesky 分解生成相关的几何布朗运动加跳跃（市场 0.2、板块内 0.6、同品种不同月份 0.95）；
- 价格落在 tick 网格上，受按交易日生效的涨跌停约束，封板时一侧没有报价；
- 维持真实行情的不变量：同一交易日内累计成交量、成交额只增不减，**最新价只随成交变动**；这正是 md-gateway 校验坏点的依据；
- 只在各品种自己的连续交易时段产生行情，交易日、夜盘归属、集合竞价与真实交易日历一致。

模拟的边界要说清楚：撮合按报价成交，没有订单簿（RK-05）；模拟价格不代表真实市场的统计特征。真实性由另外两条途径补充：回测用 2015 年以来的真实日线和官方结算价（10 文档）；新浪的真实 tick 可以用 `futrisk data record` 录制（01 §8.13），录下的数据作为真实行情样本保存，精简版的回测不使用它。

### 2.4 "无需对接真实交易所"
不对接真实交易所，但所有外部接口都按真实系统的形态设计，换成真实柜台时只替换适配器：

| 边界 | 现在 | 生产 | 核心是否改动 |
|---|---|---|---|
| 行情 | Feed A 的字段对齐 CTP 的 `CThostFtdcDepthMarketDataField`；归一化后统一为 `Tick` | CTP 行情前置（或厂商行情）适配器 | 不改动：新数据源只需实现一个传输或解码器，产出 `Tick` |
| 交易 | `SimBrokerAdapter` 连接仿 CTP 的模拟柜台 | `CtpBrokerAdapter`（只预留了接口） | 不改动：trade-gateway 的业务核心只依赖 `BrokerAdapter` 接口；切换时改服务外壳中默认的适配器工厂（目前没有配置开关） |
| 柜台权威 | 模拟柜台持久化委托、成交、持仓 | 期货公司柜台 | 不改动：本系统本来就按"影子账本、以柜台为准"设计（§5.4） |
| 参数 | `products.yaml` 中的示例值（按 2026-09-24 前后的交易所数据核对） | 按交易所和期货公司公告维护 | 不改动：参数带生效日期（TD-04） |

接入真实柜台还需要做的工作列在 §8.2。

## 3. 设计说明 1：行情数据的格式与更新频率

### 3.1 统一的内部格式
所有数据源在 md-gateway 中归一化为同一种 L1 快照 `Tick`（字段定义以 02 §7.1 为准），字段分为四组：

| 字段组 | 内容 | 设计理由 |
|---|---|---|
| 标识与时间 | 合约代码（交易所原始大小写）、交易所、交易日、自然日、交易所时间 `exch_ts_ns`、接收时间 `recv_ns`（市场时间） | 交易日由交易日历在交易所时间上**重算**，数据源自报的交易日只用来核对（Feed A 的必须一致，Feed B 的不能更旧）；DCE 夜盘 `ActionDay` 的惯例在归一化时修正；轮询记录和订阅快照中此刻不在交易时段、或者仍是上一交易日状态的合约（如 CTP 登录时推送的旧 tick、新浪在非交易时段返回的旧数据），以及本时段还没更新过的旧快照（交易所时间落在交易时段之外且不晚于收到时刻，如 CFFEX 09:25 集合竞价期间），直接跳过，不校验也不录制 |
| 价格与量 | 最新价、买一卖一价和量、开高低、累计成交量、成交额、持仓量、涨跌停价、昨结算、昨收、昨持仓、均价 | 与 CTP 的深度行情字段一一对应，生产环境换成 CTP 时语义不变；累计成交量和成交额用于计算结算价（VWAP）；数据源没给涨跌停价时按昨结算推算 |
| 来源与质量 | 数据源、源序号、标志位（集合竞价、涨停封板、跌停封板、秒级时间戳；另有一位保留的水位重置标志，现在的 md-gateway 不会置位） | 仲裁和下游消费需要知道这条数据从哪来、可信到什么程度 |
| 指纹 | 按规范化后的关键字段计算的 64 位哈希（不含时间戳） | 两个源描述同一个市场状态时指纹相同，用于标注重复（DUPLICATE）和日终规范 tick 文件的去重；跨源的先后由 `order_key` 和水位决定 |

内部格式选 CTP 风格，是因为生产环境的目标数据源就是 CTP：字段语义国内从业者都熟悉，将来接入时只需替换适配器。编码上，总线消息用 msgpack，价格用 float64，清算中的精确金额用十进制字符串（02 §4.3）。

### 3.2 各数据源的格式与频率

| 源 | 传输 | 格式 | 频率 | 序号与重放 | 定义 |
|---|---|---|---|---|---|
| Feed A | WebSocket | JSON，字段名与 CTP 相同 | 每 500ms 一个新状态（只在连续交易时段） | 全局序号 + epoch；支持续传、连接内重放、快照 | 02 §9.1 |
| Feed B | HTTP 轮询 | 厂商风格 JSON（价格为字符串、代码大写、毫秒时间戳） | 每 1s 轮询一次（连接超时 1s、读取超时 0.8s，即 `feeds.yaml` 的 `timeout_ms`） | 没有；每次返回最新快照 | 02 §9.2 |
| 新浪 | HTTP 轮询 | GB18030 文本，逗号分隔 | 默认每 1.5s，最短 1s；被限流（403/429）时间隔加倍，最长 60s | 没有；时间戳只到秒 | 02 §9.3 |

### 3.3 频率的取舍
- **500ms**：国内期货交易所通过 CTP 发布的 L1 快照约每秒 2 笔，Feed A 与之一致，演示中的行情节奏和数据量接近真实。
- **1s**：模拟厂商接口常见的限频；轮询源比推送源天然慢半拍，可信状态的晋升条件据此给轮询源"落后水位不超过 2 个轮询周期"的余量，判断轮询源是否还在送达时允许 3 个轮询周期（01 §8.13）。
- **1.5s**：新浪没有 SLA，轮询太快有被限流的风险；它的时间戳只到秒，所以只有累计成交量增加时才能推进实时行情。
- **不追求更高频率**：风控判断的是账户层面的盈亏和敞口，每秒 2 次的行情已经足够；更高频率只会增加仲裁、估值和推送的负担。全市场 CTP L1 约每秒 1600 条；完整版的 md-gateway 实测接入约每秒 1.44 万条（13 §3），2026-10-07 改写后的实现还没有复测（13 §1.3）。

### 3.4 下游的数据形态与频率

| 数据 | 形态 | 频率 | 消费方 |
|---|---|---|---|
| `md.tick.{instrument_id}` | 只有 LIVE 状态（最新值流：丢掉的状态被下一个状态取代，订阅方迟到或发布方重启时用快照追平） | 随行情 | risk-engine、api-gateway、策略 |
| `md.status` | 每个数据源的可信状态、每个合约的行情质量 | 1Hz 全量 | risk-engine（行情质量的唯一依据）、api-gateway |
| `md.event` | 数据源状态变化、质量变化、中断与恢复、缺口、坏点和数据完整性事件（事实流，不能丢） | 事件驱动 | api-gateway（仪表盘、通知）；risk-engine 订阅但目前只记日志（补数区间的影子评估未实现，TD-13）；clearing-worker 生成日报时用 `md.events` 查询 |
| `risk.snapshot.{account_id}` | 账户指标与规则状态 | 有变化时最多 2Hz，每个账户每秒至少一次保活 | coordinator、api-gateway |
| 指标样本 | 每个账户的指标 | 每秒一条写入 risk 库 | 日内曲线、日报 |
| 仪表盘 WS | 行情、账户、持仓 0.5s 一次；多账户对比、公司层、系统 1s 一次；风险事件立即推送 | — | 浏览器 |

### 3.5 中断恢复：补全缺失数据，而不产生重复或错误的风险信号
这是题目对行情接入唯一明确的容错要求。下表列出每一项风险是怎样挡住的，机制的完整描述见 01 §8.13 和 §6.4。

| 风险 | 机制 | 验证 |
|---|---|---|
| 中断期间的数据丢失 | Feed A 按序号续传和重放补洞；环形缓冲中已经没有的部分记为无法恢复的缺口；所有可信源都丢失时开一个时间窗缺口；轮询源不能重放，它自己中断期间的数据记为无法恢复（其他源可能已经覆盖） | E2E（断开 Feed A 20s，缺口补齐）；`tests/unit/md_gateway/test_mdg_integration.py` |
| 补数触发风险信号 | 补回的数据（重放、续传、订阅快照）不能成为 LIVE，只写录制和结算输入，**永远不进 risk-engine** | 同上；`tests/unit/md_gateway/test_mdg_arbiter.py` |
| 重复的行情 | 以累计成交量作跨源共享时钟：`order_key = (交易日, 累计成交量, 交易所时间)`，每个合约一个水位，只有更新的状态才能成为 LIVE；水位带最后一个 LIVE 状态的指纹每秒持久化，重启后不会把旧状态再发一次 | E2E（LIVE 行情不回退、不重复）；`test_mdg_integration.py`（重启续传） |
| 重复的告警 | 告警状态机只在状态迁移时告警；`alert_key` 带 episode，告警表以它为唯一键；恢复后确定性地重新评估 | E2E（kill risk-engine 后告警不重复）；`tests/unit/engine/test_engine_properties.py` |
| 错误的行情（坏点） | 多道防线依次过滤：交易时段、涨跌停与网格；未来时间戳；同源单调、价格只随成交变动；同成交量交叉比对：一方可信、一方不可信时判不可信的一方错误（对它投票，新来的不可信状态直接拒收），两方都可信（或都不可信）时只记 `MD_INTEGRITY` 事件、后到的状态不发布 | `tests/unit/md_gateway/test_mdg_validator.py`、`test_mdg_arbiter.py`、`test_mdg_resilience.py` |
| 错误的风险信号 | 账户的行情质量不是 OK 时状态机不迁移；熔断越线后还要 1 个不同的 LIVE 市场状态（越线那次算第 1 个）或持续 1s 才锁存，单个坏点在确认前回到阈值内就撤销。局限：确认不区分是哪个持仓合约，坏点之后先到的是别的持仓合约的行情时同样会锁存（§4.3、08 §5.2） | `tests/unit/engine/test_engine_acceptance.py`（坏点撤销、质量门控） |
| 行情"看起来在线"实际已停滞 | 行情质量 = LIVE 流是否跟得上市场：任何源（包括不可信的）出示了比水位新 5s 以上的新信息，就判为落后并计时降级（ADR-023）。局限：这需要另一个源还看得到市场；唯一在线的源连着但不再出新行情时，与市场真实无成交无法区分，质量保持 OK，只发 `MD_QUIET` 事件（08 §5.2） | `test_mdg_resilience.py` |

## 4. 设计说明 2：风控指标的选择与阈值设定

### 4.1 指标体系
题目要求至少覆盖资金维度（如账户净值、最大回撤、当日盈亏）和持仓维度（如单品种敞口、集中度）。本系统覆盖了题目举出的全部例子，并增加了合规和行情质量两个维度。指标名称和定义以 02 §7.6 为准，计算方法见 01 §8.14。

| 维度 | 题目举例 | 本系统的指标（规则 id） |
|---|---|---|
| 资金 | 当日盈亏 | 当日盈亏 ÷ 初始资金（`daily_loss`，验收口径） |
| 资金 | 最大回撤 | 日内回撤（`intraday_dd`）、距高水位回撤（`hwm_dd`），都按扣除出入金后的业绩权益计算 |
| 资金 | 账户净值 | 单位净值 = 业绩权益 ÷ 初始资金（`nav_floor`） |
| 资金 | — | 风险度 = 保证金 ÷ 权益（`risk_degree`） |
| 持仓 | 单品种敞口 | 单品种净名义敞口的使用率 = 净名义占权益比 ÷（3% ÷ 涨跌停幅度）（`product_exposure`） |
| 持仓 | 集中度 | 有效品种数 N = 1/HHI（`concentration`）；板块净名义占比（`sector_exposure`） |
| 持仓 | — | 杠杆 = 总名义 ÷ 权益（`leverage`）；涨跌停压力 = 所有持仓同时走一个不利涨跌停的亏损 ÷ 权益（`limit_stress`） |
| 合规 | — | 交易所对每日开仓手数、撤单次数、大额撤单、自成交、限仓和报单速率的限制，按使用率告警（`compliance`）；达到上限时由事前检查拒单（开仓手数在第 5 步、限仓在第 6 步、撤单次数在撤单时检查），自成交在第 9 步一律拒绝 |
| 行情质量 | — | 合约质量不是 OK 时禁开；账户超过 50% 的敞口为 UNKNOWN 时整个账户禁开 |

选择这些指标的原则：

1. **每个指标对应一种真实的亏损路径**：当日盈亏对应"今天亏太多"，回撤对应"利润回吐"和"累计亏损"，单品种和板块敞口对应"单一方向押注"，涨跌停压力对应"封板时跑不掉"，风险度对应"追保和强平"。
2. **能在事前检查中预估**：当日盈亏、风险度、单品种敞口和杠杆四条规则参与事前的 what-if，下单之前就预估"当前值 + 本单影响"，本单会让指标越过禁开级别时直接拒绝，不必等成交后再补救。局限：what-if 不计同一账户已报未成的开仓单，把一笔大单拆成几笔先后提交可以绕过它，越线要等成交之后由规则发现（08 §5.2）。
3. **能增量计算**：一个 tick 只重估持有该合约（或在该合约上有挂单）的账户，指标按增量更新，满足实时性。

### 4.2 阈值与理由
完整的默认阈值表和理由见 01 §8.14，推导与回测验证见 04 和 10 文档。阈值的推导逻辑如下：

| 推导方法 | 适用规则 | 例子 |
|---|---|---|
| 按波动率折算 | 当日盈亏 | CTA 账户年化波动约 10%~15%，日波动 σ 约 0.6%~0.95%；−3% 相当于 3~5σ，正常波动很少触及；−2%、−2.5% 两级分别用于预警和减速；−5% 是极端情况，只生成减仓计划由人确认 |
| 按涨跌停幅度反推 | 单品种敞口、涨跌停压力 | 单品种上限 = 3% ÷ 涨跌停幅度，保证单个品种走一个不利的涨跌停，亏损也不超过权益的 3%，不会单独打穿熔断线：rb（涨跌停 5%）为 60%，IF（10%）为 30% |
| 对齐行业惯例 | 距高水位回撤、单位净值、风险度、杠杆 | 回撤 8% / 12% / 15% 对齐资管产品常见的回撤控制线；净值 0.90 / 0.85 对齐产品合同常见的预警线和止损线；风险度 35% / 50% / 70% 为节前保证金上调留出缓冲（`products.yaml` 中 DCE i、m 的节前保证金配置为自 20260930 起生效，按实际收取的公司费率计算，同样持仓的风险度上升 22.2% 和 37.5%；交易所通知是自 2026-09-29 结算时起，配置晚了一个交易日，见 08 §5.2）；杠杆 3 倍 / 4 倍 |
| 交易所规则 | 合规 | 交易所对开仓手数、撤单次数、自成交、限仓的规定是硬约束：80% 预警，100% 拒单 |

阈值写在 `config/risk_rules.yaml` 中，可以按账户覆盖、热加载（01 §6.7），改动无需改代码；单品种敞口公式中的 3% 亏损预算是代码常数。规则级别的动作参数（`params`）只在级别触发时才被读取，配置校验不检查它的键名和类型，拼错的键会静默失效（08 §5.2）。

### 4.3 动作分级与信号质量
每条规则有多个级别，级别的动作从轻到重分为告警（ALERT）、限制下单（RESTRICT）、熔断（CIRCUIT_BREAK）、减仓计划（LIQUIDATE）。为了既不漏报、也不误报，每个 `(规则, 级别, 范围)` 由一个告警状态机管理（01 §8.14）：

| 机制 | 作用 | 默认值 |
|---|---|---|
| 确认 | 越线后要看到足够多**不同的 LIVE 市场状态**（只数持仓合约的新行情，越线那次评估算第 1 个）或持续足够时间才生效 | 熔断 2 个状态或 1s；集中度只按时间确认（30s）；其余级别立即生效 |
| 滞回 | 回到解除线外才解除，避免在阈值附近来回触发 | 解除线 = 阈值向安全一侧移动（阈值的绝对值 × 滞回系数），滞回系数默认 0.2，如 −3% 的解除线是 −2.4%；解除还要连续保持 3s |
| 冷却 | 告警解除后一段时间内不重复告警 | 60s，**只作用于告警级别**（ADR-022）；更严重的级别同时越线时不受冷却限制 |
| 锁存 | 熔断确认后不随指标恢复而解除 | 只有熔断和减仓级别可以锁存 |
| 质量门控 | 账户范围的规则：所持合约中行情质量不是 OK 的部分超过总名义的 10%（`quality_stale_tolerance`），或者 md-gateway 心跳丢失时，状态机不迁移，解除所需的保持计时清零 | — |
| episode | 同一交易日内同一级别第几次生效，写进 `alert_key`，保证幂等 | — |

两处局限（08 §5.2）：

- **确认不区分合约**：确认计数只看"同一账户的持仓合约有没有新的 LIVE 状态"，不要求是越线所依赖的合约。一笔落在涨跌停带内的坏点，可能被另一个持仓合约随后的一笔行情确认并锁存；待确认的熔断回到阈值内立即撤销、没有滞回，亏损在阈值附近来回时账户会在 HALTED 与其他状态之间反复切换而一直不锁存。
- **门控期间不升级**：确认和冷却按绝对时间计，门控解除的那一刻，待确认的熔断可能立即确认；但门控期间亏损即使继续扩大，也不会升级到熔断或减仓，只靠事前检查第 2 步（不是 OK 的合约禁开）和 what-if 拦截开仓。

### 4.4 实现中根据运行结果做的调整
这些调整都写在 `risk_rules.yaml` 中并附有理由（01 §8.14）：

| 调整 | 发现的问题 | 做法 |
|---|---|---|
| 按规则设置滞回 | 单位净值是 1 附近的水平量，默认的相对滞回 0.2 会把 0.90 的解除线放到 1.08，账户几乎不可能解除 | 净值规则用 0.02（解除线 0.918 / 0.867）；有效品种数用 0.1 |
| 集中度只在有一定仓位时评估 | 建仓初期、仓位很小的账户 N 很低，不代表集中度风险 | `min_gross_pct: 0.5`：总名义敞口不到权益的 50% 时视为不适用 |
| 集中度只按时间确认 | 多品种建仓时，最先成交的一两笔会让 N 在几秒内等于 1，按状态数确认会误报 | `confirm.states: 0`，持续 30s 才确认 |
| 集中度按投资授权覆盖 | 按授权只做三个黑色品种的 ACC3、只做两个股指的 ACC4、只做一组跨期套利的 ACC5，N 天然达不到 5，会整天告警 | 按授权设置下限（ACC3 2.0 / 1.5，ACC4 1.5 / 1.0，ACC5 1.0 / 1.0）；这些账户仍受板块、单品种和当日盈亏规则约束。授权范围（`accounts.yaml` 的 `products`）由策略自己遵守，事前检查不校验账户可交易的品种（08 §5.2） |
| 冷却只作用于告警级别 | 对限制下单和熔断使用冷却，等于在冷却期内关掉限制（fail-open） | 限制类级别每次重新越线都立即生效 |

### 4.5 阈值的验证
- **逻辑正确性**：状态机、事前检查、验收场景都有单元测试和性质测试（`tests/unit/engine/test_engine_rules_sm.py`、`test_engine_pretrade.py`、`test_engine_acceptance.py`、`test_engine_properties.py`；01 附录 A）。
- **规则有效性**：回测用同一个风控内核回放 2015 年以来的真实日线，对同一份数据跑"不启用规则"和"生产的日亏规则"两组配对实验，比较收益、回撤和最差单日，并列出规则生效的每一个账户日两组的盈亏之差；验收场景用合成剧本精确断言（01 §8.16）。A 层结果依赖合成的日内路径，属于模型条件下的结论；数字和结论见 10 文档。

## 5. 设计说明 3：持仓数据的来源与更新机制

### 5.1 来源
持仓**只由成交推导**，不能直接修改（事件溯源）。本系统是期货公司柜台的影子账本：自己按成交维护持仓和资金，用来做实时风控；权威数据在柜台，定期对账，以柜台为准。

| 来源 | 进入方式 | 作用 |
|---|---|---|
| 柜台成交回报 | trade-gateway 先落库、再发布到每个账户一条的有序事实流 `td.exec.{account_id}` | 盘中持仓变化的唯一来源；柜台强平等外部成交同样进入（标记为外部来源） |
| 日初快照（SOD） | clearing-worker 结算后生成，经 `eod.rollover` 推送、`settle.sod_snapshot` 拉取 | 每个交易日的起点：资金 + 以昨结算为成本的持仓 lot |
| 首日建账 | `settle.seed_sod`（REST：`/settlement/seed-sod`，ADMIN），可以带初始持仓 | 系统第一次运行时的起点；演示用 `futrisk demo` 按 `accounts.yaml` 的初始资金建账，`accounts.yaml` 写了 `initial_positions` 时一并作为昨仓（默认配置没有） |
| 出入金 | `cash.move`（ADMIN），按 EOD 状态判定记入哪个交易日 | 改变资金，不改变持仓 |
| 成交导入 | `td.import_trades`（REST：`/trades/import`，ADMIN） | 补录柜台导出的成交 |
| 柜台持仓查询 | `td.query.positions` | **只用于对账**，从不直接覆盖本地持仓 |

### 5.2 更新机制

```mermaid
sequenceDiagram
    autonumber
    participant CT as 柜台（SimBroker / CTP）
    participant TG as trade-gateway
    participant RE as risk-engine（所属分片）
    participant CW as clearing-worker
    participant API as api-gateway
    CT-->>TG: RtnTrade（成交回报）
    TG->>TG: 一个事务：回报流水 + 成交（按成交键去重）+ 游标 + outbox
    TG-->>RE: td.exec.ACC3（按序号，缺号就补）
    TG-->>CW: td.exec.ACC3（只保存成交副本）
    RE->>RE: 按交易所规则消耗 lot、计算手续费和平仓盈亏；成交与游标同一事务落库
    RE->>RE: 增量估值：只重估该合约；账户标为 dirty，本轮评估规则
    RE-->>API: risk.snapshot.ACC3（持仓与指标）、oms.order.ACC3（委托状态）
    Note over CW: 收盘后：核对成交与出入金 → 结算 → 生成下一交易日 SOD
    CW->>RE: eod.rollover → RE 拉取 SOD，换日（今仓转昨仓，成本改为结算价）
```
*这张图回答：一笔成交怎样变成持仓和指标，以及持仓怎样跨交易日延续。*

要点：

- **按账户有序、不丢不重**：`td.exec` 是事实流，发布方先落库再发布，订阅方按序号检查，缺了就重放，重放不到就按领域查询（`td.query.trades`）补齐，补不齐的账户禁开（01 §8.5）。成交按 `(交易日, 交易所, 成交号, 方向)` 去重。
- **委托回报与成交在同一条流里**：两者分开发布时，终态回报可能先于成交到达；合并成一条有序流消除了这种乱序（ADR-014）。
- **跨交易日**：收盘后 clearing-worker 结算并生成下一交易日的 SOD；risk-engine 换日时用 SOD 替换持仓（今仓转昨仓，成本基准改为结算价），并把 SOD 与自己的日终持仓比较，不一致时记一条不阻塞开仓的对账异常。

### 5.3 持仓模型
`Position(账户, 合约, 方向)` 下挂 lot，每个 lot 区分今仓和昨仓：今仓的成本基准是开仓价，昨仓的成本基准是昨结算价；同时维护数量、今仓数量和成本的累计值，事前检查读取它们的开销与 lot 数量无关（平仓成交要逐个消耗 lot）。开平与计费按交易所规则配置（01 §8.15）：

- SHFE 区分平今和平昨：不指定时的平仓按平昨处理（与 CTP 相同），平今数量超过可平的今仓时拒单（`REJECT_CLOSE_TODAY_EXCEEDS`）；
- CFFEX 按"先平当日新开仓"判定平今手续费，lot 的消耗顺序也配置为先平今仓，两者一致；
- DCE 部分品种当日开当日平时两腿按日内费率收取，只有实际被消耗掉的今仓才算日内；
- 可平量扣除在途的平仓委托，所以两张平仓单不会平掉同一手。

### 5.4 对账："以柜台为准"

| 对账 | 时机 | 不一致时 |
|---|---|---|
| 盘中持仓对账 | 每 5 分钟用 `td.query.positions` 比较；跳过有挂单的合约和 5s 内刚有成交的账户，避免把在途的变化当成差异 | 第二次不一致才判为对账异常（被跳过的轮次不清零计数），该账户禁开（平仓照常），同时自动补拉当日成交；再次比对一致即自动关闭异常、解除禁开，否则经 `risk.recon.resolve` 人工处理（02 §8.7） |
| 重启后的对账 | 预热阶段 | 对账通过、并且拿到新鲜的 LIVE 行情之前只允许平仓（等行情有超时） |
| EOD 核对 | 每日结算的第 3 步。成交三方核对：clearing-worker 的成交副本、trade-gateway 的成交摘要、risk-engine 冻结时的摘要，逐账户比较笔数、数量和哈希；出入金两方核对：clearing-worker 的副本与 risk-engine 冻结时的摘要，逐账户比较笔数和净额 | 补拉数据并重新冻结，最多 3 次；仍不一致则本次结算失败，下一交易日禁开（失效即安全）。出入金只比较净额，金额相互抵消的差异核对不出 |
| SOD 与日终持仓 | 换日时 | 记不阻塞开仓的对账异常 |

### 5.5 查询
- **按账户和品种**：REST `/positions` 可以按账户、品种、合约、交易所、板块过滤，并按其中任一维度分组；数据来自 api-gateway 的读模型，跨分片汇总；另有 CLI `futrisk positions` 和仪表盘的账户页、多账户对比页（02 §9.6）。
- **按账户查询单个账户**：risk-engine 的 `risk.query.positions` 直接给出当前持仓，包括今仓、昨仓和可平量。
- **历史**：按交易日查询结算结果中的持仓明细、平仓明细和成交记录（clearing-worker 的结算结果）。

### 5.6 多账户汇总与独立核算
- **独立核算**：每个账户有独立的资金账本、持仓和风控状态，规则按账户评估，熔断按账户锁存。性质测试专门验证"其他账户的成交不影响本账户的任何结算结果"（`tests/property/test_clearing_properties.py`）。
- **汇总**：公司层的汇总只做加总（公司权益、保证金、跨账户的品种净敞口），不共享账户状态；跨账户起作用的只有公司层的 kill switch 和公司级规则产生的限制。账户按分片分布在多个 risk-engine 中，由分片 0（coordinator）订阅各分片的快照汇总；结算时还要检查"各账户合计等于公司汇总"（`FIRM_SUM`）。

## 6. 设计说明 4："熔断"的实现方式

### 6.1 触发条件
默认配置中，`daily_loss` 规则的 `halt` 级别：当日盈亏 ÷ 初始资金 ≤ −3% 时触发，动作为熔断，确认条件为 2 个不同的 LIVE 市场状态或持续 1s，锁存（`config/risk_rules.yaml`）。其他规则也可以把某个级别配置成熔断；风控经理也可以用 `risk.halt` 人工熔断一个账户（立即锁存，不经过确认）。

### 6.2 状态与迁移

```mermaid
stateDiagram-v2
    state "正常" as NORMAL
    state "熔断待确认（HALTED，未锁存）" as PEND
    state "熔断已锁存（HALTED，已锁存）" as LATCHED
    state "重新布防" as REARM
    [*] --> NORMAL
    NORMAL --> PEND : 越过 −3%（立即禁开，撤销挂着的开仓单）
    PEND --> NORMAL : 确认前回到阈值内（撤销熔断，已撤的单不恢复）
    PEND --> LATCHED : 再看到 1 个不同的 LIVE 市场状态，或持续 1s
    LATCHED --> REARM : 风控经理审计重置（risk.reset）
    LATCHED --> NORMAL : 换日
    REARM --> PEND : 越过重新布防线（重置时的值再亏 1%）
    PEND --> REARM : 由重新布防进入的待确认，在确认前回到线内
    REARM --> NORMAL : 回到解除线外并保持 3s，或换日
```
*这张图回答：一个账户的熔断从触发到解除要经过哪些状态，每一步的条件是什么。*

图中"熔断待确认"和"熔断已锁存"都是账户状态 HALTED，区别在于 `halted_latched`；"重新布防"时熔断已经解除，账户状态由其他生效的级别决定。这张图是账户视角的简化，状态机本身的定义见 01 §8.14。

**为什么要"先禁开、再确认、后锁存"**：
- 如果越线后等确认才禁开，确认期间（最长 1s）账户还能继续开仓，不符合"达到阈值即阻止"；
- 如果越线即锁存，单个坏点（例如一笔错误的行情）就能把账户锁死一整天，需要人工处理；
- 所以越线的那一刻就禁开（不放过真实的亏损），确认之后才锁存（不让单个坏点锁死账户）。确认计数的是**持仓合约**的不同 LIVE 市场状态，之后的成交、出入金、快照行情都不计数，所以不会被非行情事件"凑满"确认。但越线的那次评估本身算第 1 个状态，不论它由什么引起（例如一笔外部成交把亏损推过 −3% 后，下一笔 LIVE 行情就能确认）；计数也不区分是哪个持仓合约，坏点之后先到的是别的持仓合约的行情时，坏点同样会被确认（§4.3、08 §5.2）。

### 6.3 生效动作

| 动作 | 实现 | 出处 |
|---|---|---|
| 拒绝新开仓 | 事前检查第 4 步：账户为 HALTED 的开仓单返回 `REJECT_ACCOUNT_HALTED`；事前检查之前先评估"脏"账户，所以越线之后的第一张单就会被拒 | 01 §5.3.1；02 §11.2 |
| 撤销挂着的开仓单 | 进入 HALTED 时，对所有挂着的开仓单（包括路由中、状态未知的）发 `route.cancel`；从没到达交易网关的委托由网关写墓碑，之后迟到的一律拒绝 | 01 §6.3、§5.3.3 |
| 撤单守护 | 熔断期间重新变为工作状态的开仓单（撤单被拒后回退、从柜台补建、重启恢复等）一律再撤 | 01 §8.14 |
| 撤单复核 | 撤单 5s 内（之后每次翻倍，最多 60s）没有结果就向交易网关复核，仍在工作的换新命令号重发；5 次之后记一条不阻塞开仓的对账异常并发出风险事件，重试继续 | 02 §8.3 |
| 只允许平仓 | 平仓单跳过账户状态与限制、资金和 what-if 三步；可平量扣除在途平仓，SHFE 区分平今和平昨 | 01 §5.3.1 |
| 纵深防御 | 交易网关拒绝超过有效期（默认 2s）的路由，防止熔断之前通过风控、延迟到达的委托被报出；公司级 kill switch 在交易网关也执行一遍 | 01 §5.3.3 |
| 通知 | 待确认阶段不产生风险事件；锁存时产生一条 `ALERT_RAISED`（严重级别 CRITICAL）；通知按 `notify_key` 去重；渠道限流时 CRITICAL 通知排队等待发送，永远不会被抑制或合并 | 01 §5.3.5；02 §9.8 |

### 6.4 解除
- **人工重置**：风控经理通过 REST 或仪表盘提交 `risk.reset`，要求 RISK_MANAGER（或 ADMIN）角色和非空理由，写审计（重置前后的账户状态、重置的级别数、理由和命令号）；重置时的指标值保存在状态机中，重新布防线随风险事件发布。状态机转为"重新布防"，重新布防线 = min(−3%, 重置时的值 − 1%)：亏损再扩大 1% 会以新的 episode 再次熔断，而且同样要经过待确认和确认。`risk.reset` 也能解除人工熔断（直接回到正常，不重新布防），还可以只针对某条规则或某个级别。
- **重置之后的开仓**：事前检查的 what-if 仍按级别本身的阈值（−3%）判断，不看重新布防线。当日亏损还在 −3% 以下时，按标记价或更差价格的开仓仍被 `REJECT_WHATIF_BREACH` 拒绝，直到亏损回到 −3% 以内（08 §5.2）。
- **换日**：新交易日开始时状态机归零，锁存默认解除（`reset_on_day_roll`）。
- **不会解除的情况**：指标回升不会自动解除；任何服务重启都不会解除；配置热加载删除或停用了规则时，已锁存的级别保留原来的规则直到重置或换日，并写一条审计。
- **热加载的例外**：如果锁存的规则和级别名都还在、只是定义被修改，状态机立即改用新定义，但保留自己的锁存标志，账户状态由级别的新动作和这个标志共同决定：只改阈值或 `latch` 时熔断仍然锁存；把动作改成熔断以外的动作（例如告警）时，账户立即离开 HALTED（`halted_latched` 随之为 false）、开仓恢复，而且不写审计（08 §5.2）。
- **公司级**：公司级规则的锁存目前没有人工解除命令，只能等换日（TD-14）；默认配置没有公司级规则。

### 6.5 跨重启保持
- 进入锁存的那个事务把状态机、告警、风险事件、账户状态和待发布的事实写在一起，并以 `synchronous=FULL` 落盘（03 DB-03）；规则触发的锁存不写审计记录，审计只记录人工操作。
- risk-engine 重启后从库中恢复状态机和锁存，HALTED 保持；恢复后的评估是确定性的，得到同样的 episode 和 `alert_key`，告警表以它为唯一键，所以不会重复告警（01 §6.5）。
- 如果提交失败，毒化闩保证进程不会带着"内存里已熔断、库里没有"的状态继续运行（01 §8.6）。
- 恢复期间开仓一律被拒（加载阶段连平仓也拒绝，预热阶段只允许平仓），所以重启窗口不会成为绕过熔断的机会。

### 6.6 验收场景
task.md 的验收场景由三层测试覆盖：

| 层次 | 测试 | 覆盖内容 |
|---|---|---|
| 多进程端到端 | `tests/e2e/test_e2e_acceptance.py`：`futrisk demo --scenario breaker --headless` 启动 supervisor 和它拉起的 8 个进程 | ACC3（初始资金 1000 万）的多头在黑色板块三段下跌中依次越过 −2% 告警、−2.5% 限制下单、−3% 熔断，每级只告警一次；熔断后开仓单被拒（`REJECT_ACCOUNT_HALTED`）、平仓单成交；kill risk-engine-1 后由 supervisor 拉起，熔断保持，告警不重复 |
| 内核级 | `tests/unit/engine/test_engine_acceptance.py` | 两种口径都触发；越线时撤销挂着的开仓单；单个坏状态在确认前回到阈值内时撤销熔断；只按时间确认；质量门控；熔断期间平仓照常；重置后重新布防；重启恢复后状态一致 |

### 6.7 刻意不做的事
- **不自动强平**：熔断只禁开，不自动平仓。−5% 的减仓计划只生成，由风控经理（或 ADMIN）确认，确认后手工下平仓单（TD-08）。自动强平在极端行情（封板、流动性枯竭）下可能以很差的价格成交，需要人的判断。完整版（`v0.1-full`）的研究级回测曾模拟熔断后自动"减半""清仓"：效果更大，但对日内路径最敏感（"先低后高"的路径上清仓为负）；精简版的回测只比较不启用规则与生产的日亏规则（10 §2.2）。
- **不对熔断使用冷却**：冷却只用于告警级别，熔断每次重新越线都重新生效（ADR-022）。
- **kill switch 不撤单**：公司级 kill switch 只拒绝新的开仓单（交易网关同时丢弃还没报出的开仓路由），不撤已挂的单；它是全公司范围的"急刹车"，撤单交给账户级熔断或人工操作。

## 7. 设计说明 5：并发模型与性能考量

### 7.1 进程划分：按故障域拆分，一致性域不拆
系统由 6 个内部服务和 2 个外部模拟进程组成（01 §5.1）。拆分的依据是故障域：

| 原则 | 做法 | 好处 |
|---|---|---|
| 故障隔离 | 行情解析、报表生成、仪表盘推送各在自己的进程中 | 任何一个崩溃或卡死都不会拖垮事前风控这条关键路径；supervisor 自动拉起 |
| 延迟隔离 | 每个服务一个进程，可以分别占用不同的核（没有绑核） | 互不争抢 Python 的 GIL；仪表盘的 JSON 序列化、结算和回测的 CPU 负载不会进入风控进程 |
| **一致性域不拆** | 持仓、资金、风控状态、事前检查放在同一个单写者（risk-engine）里 | 事前检查读到的持仓和保证金与成交处理在同一个线程中顺序执行，不会出现"同一份保证金被两笔单子同时占用"；不需要分布式锁或事务补偿 |
| 横向扩展 | 按账户分片（演示为 2 个分片：ACC1~2 / ACC3~5），分片 0 兼任公司层汇总 | 每个分片是独立的单写者，扩展时加分片 |

没有采用更细的微服务拆分（持仓服务、风控服务、订单服务分开），原因就是上表第三行：那会把一个本来单线程就能保证的一致性问题，变成分布式竞态问题（ADR-002）。

### 7.2 服务内部的并发模型

| 服务 | 模型 | 为什么 |
|---|---|---|
| risk-engine、trade-gateway | 同步 `zmq.Poller` 单线程业务主循环 + 发布线程 + 心跳线程 + 写库线程（另有后台 checkpoint 线程和按需创建的两线程卸载池） | 热路径上不引入 asyncio 调度，抖动最小；只有主循环修改业务状态，不需要锁 |
| md-gateway、clearing-worker、api-gateway、supervisor | asyncio 单事件循环 + 写库线程；md-gateway 另有录制线程，clearing-worker 另有 `spawn` 进程池 | I/O 密集（WebSocket、HTTP、总线）；CPU 重活（结算、报表、回测）放进进程池，不阻塞事件循环和心跳 |
| sim-exchange、strategy-sim（外部） | asyncio；模拟柜台的 ROUTER 在独立 I/O 线程 | 外部模拟组件 |

具体规则（01 §8.12）：
- 每个库只有一个写库线程；业务线程提交后等待确认，关键写入确认之后才发布或路由；
- risk-engine 把同一批输入（一批成交事实、一批命令、一批到期的定时器）产生的写入合并成一个事务（成组提交），提交之后才发出这一批的路由、发布和回复；
- 对外请求（重放、快照、查询、日初快照）一律异步，不阻塞主循环，所以慢操作不会让心跳丢失、被误判为死掉；
- asyncio 服务的心跳由事件循环中的定时任务发送，事件循环中禁止阻塞操作；主循环卡顿之后，对端有一个心跳周期的宽限，不会被误判为下线。

### 7.3 背压与慢消费者

| 位置 | 做法 |
|---|---|
| 行情（最新值流） | risk-engine 每轮对每个合约只保留最新价（合并），每个账户每轮最多评估一次，追数时自然合并；PUB/SUB 的高水位满了就丢，最新值流跳号时直接应用收到的最新值、不补旧值；订阅方迟到加入、发布方重启（心跳中的 epoch 变化）或 md-gateway 恢复时用快照追平 |
| 事实流 | 发布方先落库再发布，订阅方发现跳号就重放，不会因为背压丢事实 |
| 命令 | ROUTER 积压达到 1000 条返回 `BUSY`（risk-engine 的 `order.*` 命令返回 `RISK_BUSY`），客户端按指数退避重试，同一个幂等键 |
| 下单速率 | 每个账户一个令牌桶，每秒 20 张、突发 40 张 |
| 仪表盘 | 每个会话的发送队列有界：状态类数据只保留最新值，事件类数据积压过多时让客户端重新同步；超过 8MiB 或发送阻塞 10s 即断开 |

### 7.4 性能目标
设计目标（01 §1.2、§10.2）：

| 目标 | 数值 |
|---|---|
| 跨进程 tick → 规则判定（50 个账户 × 20 个合约，每秒 1000 个 tick） | p99 ≤ 3ms |
| 进程内事前检查 | p50 ≤ 50µs、p99 ≤ 250µs |
| 下单往返（客户端 → risk-engine → trade-gateway 受理） | p99 ≤ 2ms |
| 总线吞吐 | ≥ 10 万条/秒 |
| md-gateway 接入 | ≥ 1 万条/秒 |
| risk-engine 冷启动恢复（1 万笔成交） | < 3s |

### 7.5 实测结果
2026-09-26 代码冻结后，在开发笔记本上用完整版（`v0.1-full`）的 `futrisk bench` 做了一次完整测量（AMD Ryzen 7 7735H、Windows 11、Python 3.12，其他程序约占 13% CPU）。精简版删除了基准工具；总线、事前检查和 risk-engine 的被测代码与现在相同，md-gateway 已在 2026-10-07 改写，接入一项测的是旧实现（13 §1.3）。方法、全部数字和分析见 13：

| 项目 | 实测 | 目标 | 结论 |
|---|---|---|---|
| 总线吞吐 | 25.7 万条/秒，丢失 0 条 | ≥ 10 万条/秒 | 达标 |
| md-gateway 接入（改写前的实现） | 1.44 万条/秒 | ≥ 1 万条/秒 | 达标；新实现未复测 |
| 进程内事前检查（开仓单） | p50 31µs，p99 63µs | p50 ≤ 50µs，p99 ≤ 250µs | 达标 |
| risk-engine 冷启动恢复（1 万笔成交） | 3 次中位数 1.75s、最慢 1.78s（被硬杀后 1.77s） | < 3s | 达标 |
| 跨进程 tick → 规则判定（50 个账户 × 20 个合约，每秒 1000 条） | p50 0.71ms，p99 6.1ms | p99 ≤ 3ms | **未达标**（尾部） |
| 下单往返 | p50 1.2ms，p99 7.6ms | p99 ≤ 2ms | **未达标**（尾部） |

对这些结果的判断：
- **对风控本身够用**：演示负载每秒不到 40 条行情；事前检查和冷启动都在预算内；下单往返和 tick → 判定的中位数都在 1ms 左右，对 CTA 策略（每分钟几张单）不构成瓶颈。按改写前的实测，接入能力比全市场 CTP L1（约每秒 1600 条）高近 10 倍；改写后的 md-gateway 少了几道检查和 1 分钟 K 线，但这个余量要复测才能确认。
- **未达标的项**：两项延迟超标的都是尾部。tick → 判定的尾部来自单线程主循环中"等上一步做完"的排队，账户越多、持仓越多越明显，扩展办法是按账户分片；下单往返的尾部来自偶发的慢提交（Windows 文件系统）和测试环境中多个模拟服务共用一个进程（13 §4）。完整版的研究级回测另有一项回放吞吐未达标（低约 11 倍，13 §4），精简版的回测只有两个方案和确定的日内路径，全期约 1.5 分钟（10 §6），不再受它限制。

### 7.6 与性能相关的取舍

| 取舍 | 选择 | 代价 |
|---|---|---|
| 语言 | Python 3.12 + 多进程（ADR-001） | 单核性能不如 C++；靠进程隔离、增量计算和基准测试控制；热点服务可以单独用 C++ 重写，消息契约与语言无关 |
| 数值 | 盘中估值和风控比率用 float64，清算账本用 Decimal（ADR-009） | 两种口径由对账检查兜底（盘中账本与结算结果比较） |
| 落盘 | 高频写入用 `synchronous=NORMAL`，锁存熔断、kill switch、出入金、EOD 等关键事务逐次落盘（ADR-018） | 断电时可能丢最后几条高频写入，靠柜台和 trade-gateway 补回；进程崩溃不丢 |
| checkpoint | WAL checkpoint 移到后台连接（01 §8.10） | 多一个连接；换来提交不再出现 3~5ms 的停顿 |
| 估值 | 按合约建持仓索引，一个 tick 只重估持有它的账户；what-if 用标量快路径 | 代码更复杂；有性质测试保证增量结果等于全量重建 |
| 时间 | 时间戳和延迟统计用 `perf_counter_ns` 推算（Windows 上 `time.time()` 精度约 15.6ms） | 需要定期与墙钟重新对齐（每 60s） |

### 7.7 扩展路径
按以下顺序扩展（01 §8.12）：增加 risk-engine 分片 → md-gateway 按交易所拆成多个实例 → 热点服务用 C++ 重写 → api-gateway 开多副本（需要先把通知和配置协调拆给选主实例、库迁到 PostgreSQL，TD-05）。需要全公司的持久事件流时，加一个总线到 Kafka 的桥接服务做归档，热路径不变。

## 8. 设计说明 6：生产级风控系统还应具备的能力

### 8.1 本期已经具备的生产级能力
下表列出本期已经实现、并有测试或脚本证明的能力；逐项的状态也汇总在 01 §8.17。

| 能力 | 为什么生产系统需要 | 本系统的实现 | 证据 |
|---|---|---|---|
| 事前风控不可绕过 | 事后风控只能发现问题，不能阻止 | 所有委托必须经过 risk-engine 的 9 步事前检查；交易网关只接受 risk-engine 的路由 | 01 §5.2；总线白名单（`bus/whitelist.py`） |
| 失效即安全 | 任何环节失效时，默认状态必须是"不增加风险" | 行情、成交流、结算、柜台对账任一环节不可用都转为禁开，平仓照常；risk-engine 或 trade-gateway 本身不可用时，所有委托（包括平仓）都无法提交 | 01 §8.5 的故障矩阵；E2E |
| 崩溃即重启 | 带着可疑状态继续运行比停机更危险 | 提交失败或内核异常后毒化进程；所有恢复建立在持久化状态和幂等键上 | 01 §8.6；`tests/unit/risk_engine/test_re_review.py`（毒化闩）、`test_re_subprocess.py`（硬杀后重启） |
| 不丢事实、不重复处理 | 成交和告警丢一条、重复一条都是事故 | 事务性 outbox、序号补齐、幂等键、以心跳为准判断发布方重启 | 01 §8.4；`tests/unit/bus/` |
| 以柜台为准的对账 | 影子账本必然会与柜台产生差异 | 盘中定时对持仓；EOD 成交三方核对、出入金两方核对；持仓不一致和补不齐的成交缺口禁开直到处理（日初快照与日终持仓的差异只记不阻塞的异常） | §5.4 |
| 清算的正确性与可复核 | 结算错误直接导致资金差错 | 全程 Decimal；3 组手算黄金用例；交易所公式作第二道独立校验；每次结算 8 项对账检查，除日内与结算的权益比较只记 WARN 外，任一失败都不换日 | 01 §8.15；`tests/golden/`、`tests/property/` |
| 审计与权限 | 人工干预必须可追溯 | 4 种角色；所有人工操作记录操作者、角色、原因和前后状态 | 01 §8.8 |
| 接口安全 | 管理接口是攻击面 | 请求体上限、认证失败限流、WS 限额、报表下载沙箱、key 只存哈希（首次启动生成的引导 ADMIN key 另以明文写在 `<home>/secrets/` 下）、home 身份校验 | 01 §8.8 |
| 配置变更管控 | 改错一个阈值可能让风控失效 | 不可变的配置版本、两阶段提交（要么全部生效要么全部回滚）、审计；热加载删除规则时保留锁存。缺口：把仍存在的锁存级别的动作改成熔断以外的动作，会让熔断立即失效且不留审计（§6.4）；规则级别的 `params` 不校验（§4.2） | 01 §6.7；08 §5.2 |
| 备份与恢复 | 数据库损坏时要能恢复 | 每日 EOD 后 `VACUUM INTO` 备份；成交、委托等事实可以从柜台和 outbox 补回（RPO 为 0）；单个服务秒级自动重启 | 03 §8；E2E |
| 可观测性 | 值班需要知道系统是否健康 | 每秒心跳（状态、队列、速率、延迟、主循环滞后）、结构化日志、`status` / `doctor` 命令、服务拓扑页、webhook 通知 | 01 §8.7 |
| 可部署 | 能在干净的机器上装起来 | exe（17 项冒烟测试，含中文路径）和 docker compose | 01 §7.1、§7.2 |
| 性能基线 | 性能退化要能被发现 | 延迟和吞吐目标写进质量场景；完整版的 `futrisk bench` 记录机器和负载并判定是否达标，结果见 13（精简版没有基准工具，只有宽松的接入回归检查） | 01 §8.12、§10.2 |

### 8.2 尚缺的能力与建议方案
以下能力本期没有实现或只实现了一部分。它们不影响机试要求的功能，但一个真正上线的风控系统需要具备。

| 能力 | 现状 | 不具备的风险 | 建议方案 | 对应 |
|---|---|---|---|---|
| 高可用 | 单机；服务崩溃秒级重启，主机故障需要人工处理 | 风控主机故障期间不能交易（失效即安全，但影响业务） | risk-engine "主备 + 租约"：备机订阅同样的事实流热备，租约到期接管分片 | TD-01 |
| 传输加密与身份认证 | 总线不加密；演示部署只绑定本机，docker 部署绑定在 compose 网络上；调用方身份由连接方自报 | 同一主机（或同一网络）上的恶意进程可以冒充 risk-engine 或 api-gateway | 启用 ZeroMQ CURVE 并把身份与密钥绑定；REST 走 HTTPS | TD-02 |
| 真实柜台与监管要求 | 只有模拟柜台；CTP 适配器只预留了接口 | 无法实盘 | 实现 CTP 行情和交易适配器，包括登录认证、流控、看穿式监管要求的终端信息采集；先在期货公司的仿真环境中联调 | 01 §8.17 |
| 双人复核 | 熔断重置、kill switch 关闭、结算价覆盖只需一人 | 误操作或越权 | 发起人提交、另一位 RISK_MANAGER 批准后才执行 | TD-06 |
| 按账户的访问控制 | 角色是全局的，没有"只能看、只能操作某些账户" | 交易员能看到其他团队的账户 | API key 增加账户范围，读模型和命令按范围过滤 | — |
| 监控告警平台 | 指标只在心跳和仪表盘中展示；通知靠 webhook | 无人值守时发现问题慢 | 导出指标到监控平台（如 Prometheus），接入公司的告警和值班体系 | TD-07 |
| 自动减仓 | 只生成减仓计划，人工确认后手工下单 | 极端行情下反应慢 | 按计划分批下 IOC 平仓单，走同一条事前检查，行情质量不是 OK 时暂停 | TD-08 |
| 品种参数和交易日历的变更 | 不能热加载：md-gateway 在两阶段提交的准备阶段否决这类改动，整次提交放弃，只能停机后用 `futrisk config commit` 离线提交再启动；risk-engine 的品种注册表在进程内固定 | 调整保证金、手续费或交易日历都要停机；按日期生效的参数（`effective_from`、`limit_schedule`）可以提前写入，减轻这一点 | 暂存下一交易日生效的配置，在换日时切换（risk-engine 和 md-gateway 都要支持） | TD-09 |
| 大结果集 | `risk.query.*` 的应答没有分页（`td.query.trades`、重放和快照有） | 委托很多的账户查询失败 | 游标分页 | TD-10 |
| 事后审计 | 只在补数区间内出现的越线没有记录 | 事后无法说明"断线期间是否本应触发" | 影子评估器回放补数区间，只写审计 | TD-13 |
| 公司层风控的持久化 | 公司层高水位只在内存中；公司级锁存只能等换日 | 重启后公司层回撤从当天重算 | 高水位落库；增加公司级重置命令 | TD-14 |
| 时钟同步监控 | 交易时段和 EOD 按 supervisor 的市场时钟（生产中等于本机时钟）；`futrisk doctor` 检查 Windows 时间同步，md-gateway 统计接收时间与交易所时间之差，但没有持续的偏差告警 | 本机时钟偏差会让行情被误判为延迟或来自未来，时段和 EOD 的判定也会偏移 | 主机用 NTP/PTP 同步，把时钟偏差纳入监控和告警 | 01 §8.17 |
| 品种参数维护 | `products.yaml` 手工维护 | 公告调整被遗漏或录错（DCE i、m 的节前保证金生效日期就晚了一个交易日，§4.2） | 自动从交易所和期货公司公告抓取参数，变更经审批后提交 | TD-04 |
| 更全面的压力测试 | 日报中有各板块 ±3% / ±5% 冲击 | 缺少组合层面的 VaR 和情景分析 | 增加历史情景重放和组合 VaR / 预期亏损指标 | — |
| 合规报送与审计防篡改 | 审计记录只追加，但没有防篡改机制；没有监管报送 | 审计记录可被有库权限的人修改 | 审计记录做哈希链并定期归档；按需要生成监管报送所需的报表 | — |
| 交割与组合保证金 | 不做交割；DCE 组合保证金和报单申报费未实现 | 临近交割月和套利持仓的保证金偏高 | 按交易所规则实现 | TD-03 |
| 性能余量 | 负载下的 tick → 判定和下单往返尾延迟未达标；改写后的 md-gateway 没有复测接入能力 | 高负载时尾部延迟变长 | 按账户分片、降低单账户评估成本、换更快的存储；在安静的机器上复测，补上精简版的基准 | 13 §4；01 RK-12（测量波动） |

### 8.3 核对中发现的已知缺陷
2026-10-08 按代码核对时，发现以下行为与本文前面所述的设计意图不符或有缺口。它们已在正文相关处写明，处理建议汇总在 08 §5.2：

| 缺陷 | 影响 | 本文 |
|---|---|---|
| what-if 不计同一账户在途的开仓单 | 拆成几笔下单可以越过杠杆、单品种敞口、风险度的禁开线 | §4.1 |
| 熔断确认不区分合约；待确认撤销没有滞回 | 一个坏点可能被其他持仓合约的行情确认并锁存；亏损在阈值附近来回时一直不锁存 | §4.3、§6.2 |
| 质量门控期间不升级 | 非 OK 持仓超过总名义的 10% 时，亏损扩大也不熔断、不生成减仓计划 | §4.3 |
| 重置后 what-if 仍按 −3% 判断 | 重置后按标记价开仓仍被拒，直到亏损回到 −3% 以内 | §6.4 |
| 热加载改掉锁存级别的动作会解除熔断 | 改一行配置即可让熔断失效（fail-open），而且不留审计 | §6.4 |
| 唯一在线的源停滞时质量仍为 OK | risk-engine 按停止更新的价格估值，只有 `MD_QUIET` 事件提示 | §3.5 |
| 账户可交易的品种不校验 | 账户可以开授权以外的品种，只受规则限制 | §4.4 |
| 规则级别的 `params` 不校验 | 拼错的键静默失效；类型错误在级别触发时使 risk-engine 反复崩溃重启 | §4.2 |
| DCE i、m 节前保证金的生效日期晚一个交易日 | 20260929 的结算按调整前的费率计算保证金和风险度 | §4.2 |
| 出入金只两方核对笔数和净额 | 金额相互抵消的差异核对不出 | §5.4 |

### 8.4 上线前的顺序建议
1. 先处理会让风控失效的缺陷（§8.3 中的 what-if 不计在途单、热加载改动作解除熔断、熔断确认不区分合约），再还清与"能否实盘"直接相关的项：CTP 适配器、传输加密与身份认证、双人复核、时钟同步监控；
2. 再做与"出事时能否兜住"相关的项：高可用、监控告警平台、自动减仓；
3. 部署、运维和生产差距的具体步骤见 08 文档。
