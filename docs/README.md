## 1. 采用的规范

| 规范 | 用在哪里 | 选用理由 |
|---|---|---|
| **GB/T 8567-2006《计算机软件文档编制规范》** | 文档体系划分。每篇设计文档对应一种标准文档类型：系统/子系统设计说明（SSDD）、接口设计说明（IDD）、数据库设计说明（DBDD），并保留"设计决策、详细设计、需求的可追踪性"等要素 | 国内软件工程通用的国家标准，评审方熟悉 |
| **arc42 v9**（2025-07 发布，有中文版） | 整体架构说明的章节结构：目标 → 约束 → 上下文 → 方案策略 → 构建块 → 运行时 → 部署 → 横切概念 → 决策 → 质量 → 风险 → 术语 | 业界常用的架构文档模板，覆盖 GB/T 8567 对 SSDD 的要求，而且更贴近现代分布式系统 |
| **C4 模型** | 架构图按层级画：L1 系统上下文 → L2 容器（服务）→ L3 组件 | 分层看图，每张图只回答一个层级的问题 |
| **AsyncAPI 3.0 描述要素** | 通信协议文档按 servers（端点）/ channels（主题）/ operations（收发操作与命令）/ messages / schemas（负载）组织 | 事件驱动接口的事实标准。AsyncAPI 没有官方的 ZeroMQ 绑定，所以只借用它的要素组织文档，协议细节在正文里规定 |

## 3. 书写约定

### 3.1 语言与术语
- 正文用中文；标识符（服务名、主题、命令、消息类型、字段、枚举值、表名、配置键）一律用英文，并用反引号标注，如 `md.tick.{instrument_id}`。
- 领域术语第一次出现时给出中英对照，例如：逐日盯市（mark-to-market）、平今（close today）、单向大边（single-side / big-side margin）。完整的术语表见 [01-architecture.md 第 12 章](01-architecture.md#12-术语表)。
- 同一个概念全文只用一个名字。例如统一说"熔断（CIRCUIT_BREAK）"，不混用"停机""冻结"。"冻结"只用于两个固定搭配：
  - **冻结交易日**：EOD 期间的 `eod.freeze`，对应交易模式 `EOD_FROZEN`；
  - **冻结保证金 / 冻结手续费**：挂单占用的资金。

  告警状态机在行情质量不是 OK 时"保持不动"，不称为冻结。

### 3.2 规范性用语

| 中文 | 对应 RFC 2119 | 含义 |
|---|---|---|
| **必须** | MUST / REQUIRED | 绝对要求，违反即为缺陷 |
| **禁止** | MUST NOT | 绝对禁止 |
| **应当** | SHOULD | 强烈建议；不遵守时必须在文档或代码注释里说明理由 |
| **不应** | SHOULD NOT | 强烈不建议 |
| **可以** | MAY / OPTIONAL | 可选 |

规范性用语只在规定行为的句子里使用，描述性文字不用。

### 3.3 标识符命名规则

| 对象 | 规则 | 例子 |
|---|---|---|
| 服务名（service） | kebab-case | `md-gateway`、`risk-engine` |
| 服务实例（instance） | 服务名，分片服务加 `-{shard}` | `risk-engine-0`、`risk-engine-1` |
| 总线主题（topic） | 小写，用点分隔，形如 `{领域}.{类别}[.{键}]`，键放在最后 | `md.tick.rb2701`、`risk.snapshot.ACC3` |
| 命令（command） | 小写，用点分隔，形如 `{领域}.{动作}`；各服务通用的控制命令用 `ctl.` 前缀 | `order.submit`、`ctl.replay` |
| 消息与负载类型 | PascalCase | `Tick`、`OrderRequest`、`AccountSnapshot` |
| 字段、列、配置键 | snake_case | `client_order_id`、`trading_day` |
| 枚举值 | UPPER_SNAKE_CASE | `CLOSE_TODAY`、`CIRCUIT_BREAK` |
| 表名 | snake_case 复数（顺带避开 `order` 这类 SQL 保留字）。例外：日志型表和单例表可以用单数或不可数名词 | `orders`、`fills`、`rule_states`；例外有 `schema_version`、`db_meta`、`outbox`、`outbox_topics`、`api_audit`、`clock_state` |
| 合约代码 | 交易所原始大小写：SHFE/DCE/INE/GFEX 小写，CFFEX/CZCE 大写 | `rb2701`、`IF2612` |
| 账户 ID | 定长大写，演示环境为 `ACC1`~`ACC5` | `ACC3` |
| 交易日 | `YYYYMMDD` 字符串 | `20260928` |

### 3.4 时间、单位与精度
- **时间戳**：统一用 UTC 纪元纳秒（int64），字段名以 `_ns` 结尾；界面和报表按 Asia/Shanghai 显示。
- **交易日**：字段名为 `trading_day`（缩写 `td`），与自然日（`action_day`）严格区分。夜盘归属于下一交易日。
- **单位**：金额以"元"为单位，数量以"手"为单位，价格以"交易所报价单位"为单位（如 rb 为元/吨，au 为元/克）。
- **精度**：
  - 清算账本中的金额和价格用十进制精确值，数据库存规范十进制字符串，消息里用 `DecStr`（见 02 文档第 4.3 节）；
  - 盘中估值和风控比率用 float64；
  - 金额按 ROUND_HALF_UP 量化到 0.01 元，手续费逐笔取整。
- **比率**：一律以小数表示，−0.03 表示 −3%；只在界面上显示为百分比。

### 3.5 图表与代码块
- 图一律用 Mermaid，并在图下方用一句话说明这张图回答什么问题。
- 表格优先于大段文字；字段表固定为"字段 / 类型 / 必填 / 说明"四列，数据库字段表再加"约束"列。
- 协议示例用 JSON 或 YAML 代码块；实际编码是 msgpack 时，JSON 仅用于展示。

### 3.6 文档元数据与版本
- 每篇文档开头都有元数据表：编号、版本、状态、日期、适用范围、对应标准、关联文档；结尾有修订记录。
- 文档版本号为 `vMAJOR.MINOR`：设计基线是 v0.1，实现完成后发 v1.0；接口或数据结构发生不兼容变化时升 MAJOR。
- 协议有两套版本号，数据库有自己的版本号，三者各自独立，且都必须与文档一致：
  - 信封版本 `proto`，当前为 1；
  - 每个消息负载的版本 `v`，从 1 开始；
  - 数据库版本 `schema_version`，从 1 开始，每个库各自一个。
- 文档与代码放在同一个仓库（docs-as-code），**按里程碑同步**：
  - 里程碑内部的日常提交可以先改代码，文档在里程碑结束前集中修订；
  - 每个里程碑结束前，02 和 03 必须与代码一致，并且 `python scripts/check_docs.py` 的结果为 0 个问题；
  - 校验脚本直接导入代码，把文档与代码的偏差也机械地找出来：表结构与列（含可空性）、消息字段（含是否必填）、枚举取值、错误码、`FUTRISK_*` 环境变量；主题、命令与代码中注册表的对照尚未机械化，靠独立审查。

### 3.7 一致性校验
- 02 和 03 是主题、命令、消息类型、表、枚举的唯一权威定义。01 和其他文档只能引用，不得另行定义。
- 每次修订后都要做交叉校验：三篇文档中出现的主题名、命令名、负载类型、表名、端口和枚举值必须一一对应，并且都能追溯到 task.md 的需求。交叉校验分两步：
  1. **机械核对**：运行 `python scripts/check_docs.py`。它检查全部编号文档：跨文档的章节引用是否都能解析，主题、命令、负载类型、表名是否都有定义，全大写的枚举值和错误码是否都已声明，01 和 02 中的端口是否一致，以及上一节所列的与代码的对照；要求结果为 0 个问题。
  2. **独立审查**：从三个角度各审一遍：跨文档语义一致性、需求与方案覆盖度、技术正确性（含 Mermaid 语法和表格格式）。

  两步的结论都记录在各文档的修订记录中。
