## 1. 目标与方法

### 1.1 目标
目标来自 01 §8.12 和 01 §10.2 的质量场景（QS-07、QS-08、QS-11）。它们是设计目标，不是题目的要求：题目的演示负载约每秒 30~40 条行情，全市场 CTP L1 行情约每秒 1600 条。

| 基准 | 衡量什么 | 目标 |
|---|---|---|
| `bus` | 总线 PUB/SUB 吞吐：一对发布者和订阅者，项目自己的类，两个进程，TCP 回环 | ≥ 10 万条/秒 |
| `ingest` | md-gateway 接入：解码 → 归一化 → 校验 → 仲裁 → 录制交接 → K 线 → 发布，真实服务在它自己的 asyncio 运行时里 | ≥ 1 万条/秒 |
| `tick2decision` | 跨进程的 tick → 规则判定：模拟行情网关按每秒 1000 条发布，真实的 risk-engine 进程（50 个账户 × 20 个合约）完成评估并执行效果 | p99 ≤ 3ms |
| `order_rtt` | 下单往返：客户端 → 真实 risk-engine（事前检查、落库、路由）→ 模拟 trade-gateway 受理 → 应答回到客户端 | p99 ≤ 2ms |
| `pretrade` | 进程内事前检查 `check_order`（9 步，含资金和 what-if） | p50 ≤ 50µs，p99 ≤ 250µs |
| `replay` | 回测回放吞吐：五个演示策略在历史数据上，经过同一个 `EngineCore` | ≥ 10 万 tick/秒 |
| `recovery` | risk-engine 冷启动：库中有 1 万笔当日成交，从拉起进程到 RUNNING | < 3s |

### 1.2 方法
- **测的是生产代码**：跨进程的基准启动真实的服务进程（`futrisk svc risk-engine` 等），对面是记录时间戳的模拟服务；进程内的基准直接调用生产的类。
- **时间戳**：一律用 `perf_counter_ns`。Windows 上它读 QPC，所有进程共用一条时间线，跨进程延迟可以直接相减（启动时校验）；`time.time()` 在 Windows 上只有约 15.6ms 精度，不使用。
- **百分位**：最近秩（nearest-rank）百分位；每一项同时给出样本数、p50、p90、p99、最大值。
- **负载记录**：运行前和运行中采样整机 CPU 利用率，分出本基准进程树和"其他程序"的部分；另测调度抖动（一个线程空转 2s，记录超过 1ms 和 5ms 的间隙）。后台负载高时，结果偏悲观，报告会注明。
- **判定**：每项基准有一行主指标（表中加粗），与目标比较得出 PASS 或 MISS；其余行是用来定位原因的诊断数据。

## 4. 分析

**达标的 4 项**：总线吞吐是目标的 2.6 倍，行情接入是 1.4 倍，事前检查的 p99 只用了预算的四分之一，冷启动恢复在 2s 以内（被硬杀后同样如此）。这些是风控正确运行所依赖的能力：演示负载约每秒 30~40 条行情，全市场 CTP L1 约每秒 1600 条，接入能力有近 10 倍余量。

**tick → 判定（p99 6.1ms，目标 3ms）**：中位数 0.71ms、p90 1.13ms 都在目标内，超出的是尾部。拆开看，尾部主要在第 1 段（p99 4.6ms）：risk-engine 是单线程主循环，一条 tick 到达时如果循环正在处理上一步（评估其他脏账户、落库、发心跳），它要等这一步结束；第 2 段（本步内的计算）p99 1.9ms。账户越多、每个账户持仓越多，每一步越长：每个账户都持有全部 20 个合约时，每条 tick 都会让 50 个账户全部变脏，p50 升到 8.6ms（这时循环按设计合并 tick，每次评估约 5.9 条）。改进方向：一个分片少放一些账户（按账户分片是现成的扩展方式，01 §5.2）；降低单个账户的评估成本；把落库和心跳移出评估的关键路径。对本题的演示负载（5 个账户、每秒几十条 tick），这一延迟在 1ms 以内。

**下单往返（p99 7.6ms，目标 2ms）**：中位数 1.2ms、p90 1.7ms，同样是尾部超标。risk-engine 进程内的处理 p99 只有 1.2ms，尾部来自两处：risk.db 提交偶尔很慢（最大 8ms，Windows 上的文件系统写入），以及测试用的模拟 trade-gateway 与其他模拟服务共用一个 Python 进程和 GIL。CTA 策略每分钟下几张单，毫秒级的往返延迟不构成瓶颈；如果要做到 p99 ≤ 2ms，方向是换用更快的存储或 Linux 主机，并让风控落库与应答并行（目前先提交再应答，这是"先落库再发布"的一致性要求，01 §8.4）。

**回测回放（9265 tick/秒，目标 10 万）**：差约 11 倍（TD-15）。每个行情状态 p50 105µs，时间主要花在逐个账户的估值和规则评估（静态账簿也只有 2.5 万 tick/秒）和策略的逐 tick 计算上，都是纯 Python。它不影响实盘，只影响长周期回测的耗时：`default` 配置（2015 年至今、20 条随机路径、多组敏感性分析）用 15 个进程也要数小时（10 §6）。改进方向：估值的标量快路径、策略向量化，或把热点移到编译扩展。

**与首次测量的比较**：2026-09-25 在机器负载较高时的首次测量中，总线 9.7 万条/秒、下单往返 p99 10.8ms、tick → 判定 p99 27.5ms、冷启动 3.4s 均未达标。之后的性能修订（GC 策略：调高回收阈值，服务进入 RUNNING 时把启动期间的对象冻结到永久代；服务进程只导入自己需要的模块；发布热路径；主循环只读取有消息的套接字）与更安静的测量环境共同带来了本次的结果，两者的贡献没有分开测量。

## 5. 如何重跑

基准工具只在完整版中，先检出 `v0.1-full` 标签，测完再切回精简版的分支：

```powershell
git switch --detach v0.1-full
futrisk bench                     # 全部 7 项，约 3 分钟；结果表打印到控制台
futrisk bench --out bench.md      # 同时写出 Markdown 表格
futrisk bench order_rtt pretrade  # 只跑其中几项
futrisk bench --quick             # 小规模，每项几秒，只看趋势
futrisk bench --profile --json    # 带 cProfile，输出 JSON
git switch -                      # 回到原来的分支
```

测量前关闭其他占用 CPU 的程序，电源计划设为"高性能"，接通电源。结果依赖机器，不同机器之间只比较 PASS / MISS 和数量级。
